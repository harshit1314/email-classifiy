# AI Email Classifier - Detailed Project Discussion

This document serves as a comprehensive technical deep-dive into the AI Email Classifier project. It covers the datasets, machine learning algorithms, programming languages, module implementations, graphical user interface (GUI), and test cases used throughout the system.

---

## 1. Detail Discussion on Dataset

The system's dataset strategy involves both **pre-trained corpora** (via Hugging Face transformers) and **proprietary/historical datasets** (for fallback algorithms and entity extraction).

### A. The Enron Email Corpus (Base Training Data)
To build a robust baseline for our classical machine learning models, the system was originally bootstrapped using a subset of the famous **Enron Email Corpus**.
- **What it is**: A massive database of over 600,000 emails generated by employees of the Enron Corporation, widely used in NLP research.
- **How we used it**: We extracted, cleaned, and labeled a subset of this corpus to reflect modern corporate departmental structures (HR, Finance, Sales, Marketing, Support). This provided the fundamental vocabulary, syntax, and structural patterns present in real-world corporate communications, serving as the training bedrock for our TF-IDF vectorizers and classical algorithms.

### B. Zero-Shot Pre-Trained Corpus (DistilBERT)
The advanced categorization engine leverages the `distilbert-base-uncased-mnli` model. This model was trained on the **Multi-Genre Natural Language Inference (MNLI)** dataset, allowing it to understand the semantic relationship between a premise (the email body) and a hypothesis (e.g., "This email is about Finance").

### C. Live Database (MongoDB / SQLite)
The system continuously builds its own dynamic dataset. Every ingested email, along with its ML-assigned classification, confidence score, sentiment, and user-provided corrections, is stored in the database. This acts as a feedback loop for the **zero-shot keyword boosting mechanism**.

## 2. Algorithms / Techniques Used

The project employs a hybrid approach, combining deep learning transformers with classical NLP, TF-IDF vectorization, and rule-based systems to balance accuracy and computational efficiency.

### A. Classical Machine Learning & Feature Extraction
Before diving into deep learning, the system heavily utilizes traditional NLP algorithms to process and classify text quickly:
- **TF-IDF (Term Frequency-Inverse Document Frequency)**: A statistical measure used to evaluate how important a word is to a document in a collection or corpus. We use TF-IDF vectorization to translate raw email text (subject lines and bodies) into numerical feature matrices. It naturally down-weights common words (like "the", "and") and highlights domain-specific keywords.
- **Logistic Regression**: Used as a fast, interpretable baseline algorithm. It takes the TF-IDF feature matrix and applies a sigmoid function to predict the probability of an email belonging to a specific department. It excels in binary and multi-class text classification when classes are linearly separable.
- **Random Forest Classifier**: An ensemble learning method that constructs a multitude of decision trees at training time. In our "Improved Classifier", Random Forest takes the TF-IDF features and outputs the mode of the classes produced by individual trees. It is highly resistant to overfitting and handles the high-dimensional sparse data generated by TF-IDF very well.

### B. DistilBERT Zero-Shot Classification
- **Technique**: Natural Language Inference (NLI) used for Zero-Shot Text Classification.
- **How it works**: The `Transformers` library pipeline formulates the classification task as an entailment problem. It checks if the email text "entails" the labels `["HR", "Finance", "Sales", "Marketing", "Support"]`. DistilBERT is a smaller, faster, and lighter version of BERT that retains 97% of its language understanding capabilities while being 60% faster.
- **Keyword Boosting**: To avoid heavy fine-tuning, when a user manually corrects a misclassified email, the system extracts unique keywords and maps them to that department. When future emails arrive, the system scans for these keywords and artificiality boosts the probability score for that specific department before the final softmax decision is made.

### C. Rule-Based Natural Language Processing (NLP)
- **Sentiment Analysis**: TextBlob and VADER (Valence Aware Dictionary and sEntiment Reasoner) are used for rule-based sentiment detection. We specifically disabled the DistilBERT sentiment model to prevent Out-Of-Memory (OOM) crashes on constrained hardware, opting for deterministic lexicon-based approaches to reliably label emails as *Positive*, *Negative*, or *Neutral*.

## 3. Language Used

The project is structured as a modernized full-stack web application.

### A. Python 3.8+ (Backend)
- **Why Python?**: Python is the undisputed industry standard for Artificial Intelligence and Data Science. It provides native support for `PyTorch`, `Transformers`, and `scikit-learn`.
- **FastAPI**: The backend web framework. FastAPI handles asynchronous (`async/await`) API routing, meaning it can process multiple ML inferences and database queries concurrently without blocking the main event loop.

### B. JavaScript / React 18.2 (Frontend)
- **Why React?**: Building an intricate dashboard requires a reactive, component-based UI. React allows the dashboard to update charts, tables, and email lists in real-time as data changes.
- **Vite**: The build tool and development server, chosen over Create-React-App for significantly faster Hot Module Replacement (HMR) and optimized production builds.

## 4. Implementation of All Modules

The architecture follows a microservices-inspired monolithic design, breaking the system into specific domain services.

### A. Ingestion Service (`ingestion_service.py`)
Responsible for fetching data from external APIs (Gmail, Microsoft Graph/Outlook). It parses raw MIME email formats, extracts headers, sender info, bodies, and attachments, standardizing them into a clean Python dictionary format.

### B. Processing Service (`processing_service.py`)
This is the "Brain Orchestrator". When an email arrives, it executes the following steps pipeline:
1. Triggers the **Classifier** (DistilBERT or Random Forest/Logistic Regression fallback) to deduce the department.
2. Triggers the **Sentiment Service** to detect tone.
3. Triggers the **Entity Extraction** to pull out dates/money.
4. Aggregates this data into a comprehensive `classification_result` object.
5. Saves the raw output to the database via `logger.py`.

### C. Action & Department Routing Service (`action_service.py`)
Once processed, this service looks at the assigned department (e.g., `HR`) and maps it to a tangible action. It looks up the routing logic (e.g., "Route HR emails to `hr@company.com`") and executes the forwarding or tagging action via SMTP/API.

### D. Retraining Service (`retraining_service.py`)
Tracks user corrections. Upon an admin triggering "Retrain", it fetches the corrected emails from the database, extracts highly frequent terms missing from the base keyword lists, and updates the in-memory boosting dictionaries.

## 5. GUI (Graphical User Interface)

The frontend is built with **Tailwind CSS** and **Radix UI**, providing an enterprise-grade, accessible interface.

### A. Main Dashboard
- **Analytics View**: Utilizes `Recharts` to draw real-time graphs showing volume over time, category distribution pie charts, and confidence distribution histograms.
- **System Health**: Cards displaying uptime, processed count, and API connection status.

### B. Email Classification View
- An interactive inbox clone. Users can click on an email to open a detailed modal showing the predicted department, confidence progress bars, and extracted entities.
- Includes a "Manual Override" dropdown where admins can correct the AI's prediction.

### C. Settings & Models
- UI toggles to switch the active ML model (Basic TF-IDF vs DistilBERT vs Random Forest).
- Interactive buttons to safely execute model retraining or test database connections.

## 6. Test Cases

The application enforces stability through a suite of test scripts designed for automated and manual execution.

### A. Unit Testing (Backend logic)
- **`test_bert_departments.py`**:
  - *Input*: "Please approve the Q3 budget."
  - *Expected Output*: Department `Finance`, Confidence > 0.60.
  - *Purpose*: Ensures the zero-shot and TF-IDF pipelines correctly map standard business jargon to our 5 core departments.

### B. API / Integration Testing
- **`test_500.py`**:
  - *Input*: Call `GET /api/email/status` without prior Gmail authentication.
  - *Expected Output*: HTTP 200 OK with `{"gmail_connected": false}`, rather than a Python unhandled exception (HTTP 500).
- **`test_retrain_api.py`**:
  - *Input*: Call `POST /api/ml/retrain`.
  - *Expected Output*: HTTP 200 OK with `{"status": "completed", "keywords_added": 5}`.

### C. System Resilience / OOM Testing
- *Scenario*: Boot the FastAPI server on a machine with <4GB RAM.
- *Expected Outcome*: Server boots successfully. (Verified by disabling the heavy deep-learning sentiment model and ensuring only the chosen categorization model is loaded into memory).

### D. Frontend/GUI Test Cases (Manual)
- *Scenario*: Click a pie chart wedge on the Dashboard.
- *Expected Outcome*: The email data table filters to show only emails belonging to the clicked department category.
- *Scenario*: Click "Retrain Model" in settings.
- *Expected Outcome*: Button shows a loading spinner, preventing double-clicks, and displays a success toast notification within 5 seconds based on keyword extraction updates.
